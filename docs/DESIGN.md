# GitHub 速读设计规范

本规范借鉴 Steve Krug《Don't Make Me Think》的可用性原则：界面应尽量自解释、采用熟悉的惯例、建立清晰视觉层级、让可点击元素显而易见，并删除不帮助用户完成任务的文字。它不是对书籍版式或文字的复制。

## 产品命名

- 产品名：**GitHub 速读**。
- 一句话说明：**保存仓库，先看结论**。
- 核心对象统一称为“解读”，不用“报告”“AI 分析结果”“内容摘要”等近义词。
- 完整列表统一称为“工作台”，不用“后台”“收件箱”“管理中心”。

## 信息层级

每张解读按照用户决策顺序排列：

1. 一句话结论
2. 项目概述
3. 关键亮点与需要留意的风险
4. 建议下一步
5. 元数据和管理操作

弹窗只展示前四项；工作台展示完整信息。

## 行为规范

- 当前页面的主操作只有一个：“生成解读”或“查看完整解读”。
- 次要入口使用文字按钮：“打开工作台”“模型设置”。
- 生成完成后在原地显示结果，不要求用户先跳转。
- “查看完整解读”进入工作台并定位到对应仓库。
- 工作台默认按 `analyzedAt` 倒序，状态或分类修改不得改变解读顺序。
- 工作台每页展示 10 条；筛选或搜索条件变化时回到第一页，从弹窗进入时自动定位到目标所在页。
- 禁用、加载、成功和失败状态必须出现在触发操作附近。
- 模型默认自动选择并展示实际结果；手动模型名属于高级设置，不作为首次配置的必填判断。

## 视觉规范

- 使用系统无衬线字体，优先保证快速扫描。
- 绿色只表达主操作、当前定位和成功状态。
- 每个表面最多一个实心主按钮。
- 正文控制在短段落，风险与亮点使用短列表。
- 不用仅作装饰的图标、隐喻或营销文案。
- 控件保持可见标签，不以 placeholder 代替字段名。

## 文案规范

- 按钮使用“动词 + 对象”：生成解读、查看完整解读、保存设置。
- 成功信息说明结果在哪里：“解读已保存，重要信息已显示在下方。”
- 错误信息说明原因和下一步，不只写“失败”。
- 使用用户语言，避免暴露内部名词，例如 completion、payload、worker。
